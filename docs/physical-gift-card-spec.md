# 統一實體卡隨機禮包規格

本規格供 Backend、Admin 與前台實作同一張實體卡的領獎流程。卡片可用作名片，也可放進每次宅配的箱子；所有卡片的版型、文字與 QR Code 完全相同。QR Code 是領獎入口，領取次數由會員活動資格與正式包裹紀錄決定；宅配隨箱禮須在物流確認收件完成後才開放。

狀態：實作與驗收基準。更新日期：2026-10-05。功能已於 `codex/physical-gifts` 的 Backend、Admin、前台隔離工作目錄實作；正式資料庫 migration、部署與真實物流驗收尚未執行。實作入口與本地驗證請見同目錄 `physical-gift-card-handoff.md`。

## 已確定的產品規則

| 項目 | 規則 |
| --- | --- |
| 印刷 | 只做 QR Code 紙卡，不使用 NFC；整張卡完全相同，不印每張專屬 QR Code、序號或兌換碼 |
| 名片見面禮 | 每個會員帳號在同一個見面禮活動只能領一次 |
| 宅配隨箱禮 | 每個正式出貨包裹建立一份待啟用資格，綁定出貨紀錄關聯的會員帳號；物流確認宅配送達或消費者成功取件後才可領 |
| 重複購買與收件 | 同一帳號收到不同包裹，可以各領一份；不套用每帳號每活動一次的名片限制 |
| 領取單位 | 每次確認開啟一份指定資格；一次請求不批次核銷，也不自動轉領下一份 |
| 重複掃描 | 開啟同一個頁面，不新增資格、不重新抽獎、不直接入帳 |
| 重試 | 同一資格沿用同一筆領取紀錄、隨機結果與入帳識別碼 |
| 獎勵 | 首版為站內 Points 隨機禮包，沿用每日任務的禮包呈現與既有 Points 帳務能力 |

同一帳號若尚未領取名片見面禮，又有兩份已確認收件且預算就緒的宅配資格，會看到三份可領禮包；必須分別確認開啟。尚在配送的宅配禮包只顯示等待狀態。系統無法從相同的卡片判斷這次掃描來自名片或宅配，所以兩類資格依各自規則提供；名片見面禮不受物流門檻限制。

本方案保證每份資格至多核銷一次，入帳可安全重試。固定 QR Code 無法證明現場交卡或實際拿到某個箱子，也無法把每一次相機掃描辨識成獨立的實體事件。名片入口可被轉傳，但同一帳號同活動仍限領一次；宅配資格由出貨紀錄提供，轉傳連結不會增加份數。

知道網址或保留舊卡的人可隨時開啟頁面，但收件確認前不能領取新包裹的禮包。確認收件後，可直接開啟收藏的網址領取，不必再次掃描新卡。物流門檻控制開放時機，不能證明使用者已拆箱或手上持有本次卡片。

## 固定入口與卡片文案

建議固定入口為 `https://<正式站網域>/gift`。此網址是規格占位，須在路由上線、正式網域確認後才產生印刷用 QR Code。網址不帶活動 ID、會員 ID、出貨單 ID 或獎池版本；活動調整由後端設定處理，卡片可長期使用。

前台以固定入口導向目前語系的禮包頁。登入與返回流程需保留 `/gift` 目的地，登入後仍可查看相同帳號的資格。頁面讀取與連結預覽都不能執行領取。

建議卡片文案：

> 有份隨機禮包等你開啟
>
> 掃碼登入，查看你的見面禮與宅配禮包。
>
> 每份限領一次，宅配禮包於物流確認收件後開放。

不使用「每掃一次就送一次」或「每張卡都能再領」等無法由此方案兌現的文字。

## 身分與出貨資格

會員身分使用後端驗證登入後取得的 canonical `userId`，沿用現有 `requirePlatformUserId` 語意。API 不接受前台指定領取人的 `userId`、錢包、獎勵金額或中獎結果。

「收件帳號」在本規格中指出貨紀錄關聯的 `LogisticsOrder.userId`。不以姓名、電話、地址或掃描裝置推測會員身分。其他帳號掃描相同卡片，只能查看自己的資格。

宅配資格由已提交成功的正式出貨事實產生，初始為 `PENDING_DELIVERY`。現有商家直送流程以 `IN_TRANSIT` 記錄寄出；綠界流程必須經既有通知驗證、狀態正規化與訂單版本檢查，確認包裹已進入配送。建立資格不等於開放領取。

只有本包裹的有效收件完成證據，才可通過物流門檻，再完成預算保留並轉為 `AVAILABLE`。若有效通知直接到 `DELIVERED`，以同一來源鍵補建資格並檢查啟用條件；不能因漏掉配送中通知而漏發，也不能新增第二份。

`READY_TO_BOOK_ECPAY`、`ECPAY_BOOKING_CREATED`、寄件標籤列印與物流預約成功都不能單獨產生禮包。商家現場自取 `STORE_PICKUP` 不納入首版；綠界超商配送的消費者取件屬於本方案，須與商家自取區分。配送異常通知不視為新包裹。

目前 `LogisticsOrder` 沒有逐箱的包裹明細。本需求的獎勵單位是實際寄出的箱子，因此實作需新增穩定的包裹識別，例如 `LogisticsParcel.id`：

- 一張出貨單一箱時建立一筆包裹；拆成兩箱時建立兩筆，每筆各有一次資格。
- 重印寄件單、更正物流編號、重送 webhook、重跑同步都保留原包裹 ID。
- 真正另外寄出的補寄包裹建立新 ID；修復原本漏發的獎勵則使用原 ID。
- 包裹數由有權限的裝箱或出貨流程記錄，會員端不能自行增加。
- 每箱須綁定可追溯的物流單與收件證據；一箱送達不能直接解鎖同出貨單其他箱子。若物流單採多件共同追蹤，需明確確認其完成狀態涵蓋所有件數，否則逐箱等待有效證據。

## ECPay 物流啟用條件

依 2026-10-05 檢視的綠界官方文件，物流狀態通知會送至 `ServerReplyURL`。必須區分「包裹到店」與「消費者完成取件」，並依物流子類型判讀，不使用狀態文字模糊比對或通用成功碼。參考 [物流整合 API 通知](https://developers.ecpay.com.tw/7420/) 與 [全方位物流 API 通知](https://developers.ecpay.com.tw/10127/)。

| 物流事實 | 後端正規化狀態 | 宅配禮包 |
| --- | --- | --- |
| 已正式出貨、配送途中 | `IN_TRANSIT` | 建立或保留待啟用資格，不能領 |
| 已送達超商、通知可取件 | `READY_FOR_PICKUP` | 仍等待消費者取件，不能領 |
| 消費者成功取件、宅配送達 | `DELIVERED`，且具有本包裹的有效收件證據 | 通過物流門檻；預算就緒才可領 |
| 配送異常、未知代碼 | 異常或僅保存原始資料 | 不因這筆通知啟用 |
| 取消、退回中、已退回 | `CANCELLED`、`RETURN_IN_PROGRESS`、`RETURNED` | 未領資格撤銷；已領依帳務更正規則處理 |

官方通知文件的超商範例：7-ELEVEN B2C／C2C 的成功取件碼為 `2067`，全家與萊爾富 B2C／C2C 為 `3022`；到店碼如 `2063`、`2073`、`3018` 不能作為成功取件。這些範例不能代替其他物流的對照表，亦不能跨子類型套用。宅配須依實際啟用的物流商核對配送完成碼。[完整貨態代碼表](https://developers.ecpay.com.tw/7440/) 會更新，實作與上線驗收需保存採用的版本及各啟用子類型的測試案例。

沿用後端 `handleServerNotify`、`applyEcpayNotification` 與 `ecpay-status.ts` 的驗證、事件時間、重複通知、狀態轉移及更正處理，再新增包裹綁定與禮包啟用服務。傳統通知由已驗證的 `RtnCode` 取得貨態；全方位加密通知的 `RtnCode = 1` 是 API 成功，貨態需讀取 `LogisticsStatus`，不能看到成功碼就啟用。

新服務必須確認特店、`MerchantTradeNo`、物流交易 ID、子類型及目前有效的寄件批次與包裹綁定一致，且屬於寄往收件人的正向配送。退件到寄件門市、換單後舊物流單的通知、其他箱子或其他會員的通知都不能通過門檻。物流編號更正沿用包裹 ID，但需保存綁定歷史與當次有效範圍。

以已提交的正規化狀態與收件證據作授權依據。僅更新 raw status、事件時間無效、過期通知、未通過版本檢查、未知代碼及未接受的狀態回退，都不能直接建立收件確認。後續有效的配送完成撤銷／更正，須取消尚未核銷的收件確認並恢復 `PENDING_DELIVERY`；日後再次取得有效證據仍使用原資格。單純較舊的配送中通知不能把已確認的狀態倒退。

`MERCHANT_DIRECT` 不靠 ECPay 通知完成門檻。若無可驗證的物流商介接，需由具權限的營運人員記錄收件證據、確認時間、操作者及原因；一般狀態編輯不能自動成為禮包授權。會員按「我已收到」不能自行解鎖。

綠界通知不是即時傳送，超商貨態另有批次交換延遲。頁面應顯示「等待物流確認，收件後將開放」，提供重新查詢本人禮包狀態的入口；不得以「已收到」的會員回報取代可信物流資料。[綠界貨態追蹤說明](https://support.ecpay.com.tw/5979/)。未收到通知時，由後端排程以官方查詢 API 補查，再走相同驗證與正規化流程。查詢需限制頻率、退避及對帳；每次掃 QR Code 不直接呼叫綠界，也不以查詢按鈕產生資格。

## 建議資料模型

以下名稱是待實作的設計，並非既有資料表。

| 模型 | 主要欄位與責任 |
| --- | --- |
| `PhysicalGiftProgram` | 名片或宅配方案、名稱、資格建立開關、領取暫停開關、獎池版本、預算與操作紀錄 |
| `PhysicalGiftPolicyVersion` | 已發布且不可覆寫的 Points 範圍、機率、展示內容及快照雜湊 |
| `LogisticsParcel` | 穩定包裹 ID、出貨單 ID、會員 ID、箱次、正式出貨時間、配送狀態、目前物流綁定及歷史、收件確認時間與證據；不以可更改的物流編號作主鍵 |
| `PhysicalGiftEntitlement` | 資格 ID、全域唯一來源鍵、會員 ID、方案 ID、包裹 ID、資格時間、獎池快照、物流門檻、收件來源事件關聯、預算保留與狀態 |
| `PhysicalGiftClaim` | 每份資格唯一的一筆領取、會員與收款錢包快照、固定隨機結果、入帳識別碼、Points ledger 關聯與重試狀態 |

來源鍵必須由後端產生：

```text
名片資格 sourceKey = WELCOME:<campaignId>:<userId>
宅配資格 sourceKey = SHIPMENT:<parcelId>:PACKAGE_GIFT
領取唯一限制      = UNIQUE(entitlementId)
入帳識別碼        = physical-gift:<entitlementId>
```

`PhysicalGiftEntitlement.sourceKey` 與入帳識別碼都必須有資料庫唯一限制。宅配來源鍵不包含會員、方案版本或日期：同一包裹不能因改綁帳號、切換活動、更新獎池或跨日而再產生資格。名片活動更新獎池也不更換 `campaignId`；另開一次見面禮必須是有操作紀錄的新活動。

獎池快照在資格建立時固定。領取時固定收款錢包、抽中等級及整數 Points 金額；重試時不得改用後來切換的錢包。Points raw amount 使用既有 18 位單位轉換並以字串傳遞，避免 JavaScript 浮點帳務誤差。

## 隨機獎池與預算

首版建議提供與每日完成禮包相同的設定選項。本機每日禮包 v3 的參考設定如下；名片及宅配活動啟用時，Admin 必須明確選用已發布版本，不能從程式常數默默啟用。

| 等級 | 等級機率 | 等級內 Points 範圍 |
| --- | ---: | ---: |
| SILVER | 35% | 1 至 3 |
| GOLD | 50% | 4 至 6 |
| PLATINUM | 15% | 7 至 10 |

先依權重選等級，再在該等級內均勻選一個整數金額。機率驗證需確認合計為 100%，範圍是正整數、上下限有效且符合既有抽樣器限制；不能使用無效設定時退回最後一級的容錯行為來掩蓋錯誤。前台顯示範圍與機率須來自同一份版本快照。

隨機值由後端密碼學隨機來源產生，參考現有 `node:crypto.randomInt` 抽樣器。這是平台提供的站內 Points 禮包；不宣稱鏈上可驗證隨機數。抽樣結果只在領取交易成功提交後成立，回應丟失或工作排程重跑不得重抽。

活動需設定有限預算。資格可領取前，依該份快照的最大可能獎勵保留預算；核銷時把最大保留額改為實際中獎額，釋放差額。入帳完成只改變結算狀態，不能再扣一次預算。撤銷未領資格時，保留額只能釋放一次。

宅配出貨時先建立 `PENDING_DELIVERY`，確認收件後才嘗試保留預算。收件已確認但預算不足時標記 `WAITING_FUNDS`，後台告警、前台顯示準備中。補足後使用原資格及原獎池快照恢復；尚未確認收件的資格即使補足預算也不能解鎖。不能刪除再建，也不能為了符合剩餘預算重抽較小金額。禮包處理失敗不得回滾已成功的實體出貨。

物流門檻與預算保留分開保存；`AVAILABLE` 必須同時符合有效收件確認、預算已保留、未撤銷且未核銷。活動暫停另於領取交易檢查。若收件確認被有效更正撤銷，未領資格回到等待收件並且只釋放一次保留額；重新確認時再以原資格保留預算。名片資格不檢查物流門檻。

## 領取交易與入帳

掃碼與 GET 只查詢。名片見面禮在使用者確認領取後，由後端檢查活動與帳號資格，建立或取得唯一來源鍵；宅配領取只能使用已由出貨流程建立的資格。

一次 POST 的處理順序如下：

1. 驗證登入帳號與資格所有權。取得已有 claim 時返回同一筆；已領紀錄不會因活動關閉而消失。
2. 開啟資料庫交易，依固定順序鎖定方案預算、來源出貨單與包裹或名片來源、資格。與撤銷及預算修改流程使用相同鎖定順序。
3. 重新檢查資格狀態、來源、領取暫停、預算及後端選定的收款錢包；宅配另確認本包裹目前仍具有有效收件證據，沒有取消、退回或配送完成更正。即使啟用工作尚未同步更正，舊的 `AVAILABLE` 也不能通過。前台先前看到的可領狀態不能當授權依據。
4. 使用固定獎池快照抽樣，建立唯一 claim，將資格標記為 `CLAIMED`，保存結果與入帳識別碼，並完成預算轉換。
5. 同一交易保存可恢復的發獎工作。交易提交後才回應，並嘗試立即入帳。
6. 發獎服務使用既有 Points repository，以固定識別碼入帳；保存 Points ledger ID 後標記 `GRANTED`。

正式出貨、收件確認、更正／撤銷及發獎工作需有交易內 outbox 或等效的耐久工作紀錄。單靠記憶體 callback 不足以承接物流狀態已成功提交、程序卻在資格更新前重啟的情況；既有訂單通知也不能當作耐久啟用工作。物流通知完成驗證、狀態保存及耐久工作保存後依原介面回覆綠界，不等待使用者開禮包或 Points 入帳。

另以週期性對帳補建有效出貨漏掉的資格、啟用已確認收件卻未更新的原資格，以及補處理配送完成更正或退回事件。對帳仍須檢查最新有效物流來源、預算與唯一鍵，不把每筆重送通知當作新的資格。

工作排程可能重複執行，實際入帳效果必須至多一次。尤其「Points 已入帳、claim 尚未標記成功」後程序重啟時，重試要取得既有 ledger，再修復 claim 狀態。資格不可回到可領，也不可建立另一筆 claim。數次失敗後進入人工處理，保留原結果及識別碼。

Points 入帳沿用帳戶凍結、欠額抵扣與估值規則，不繞過既有帳務政策。前台應區分「已開出」與「已入帳」，並以帳務回傳的餘額呈現實際可用 Points。

## 狀態與異常處理

資格狀態：`PENDING_DELIVERY`、`WAITING_FUNDS`、`AVAILABLE`、`CLAIMED`、`REVOKED`。宅配資格先檢查物流門檻，未通過就維持 `PENDING_DELIVERY`；確認收件後才依預算進入 `WAITING_FUNDS` 或 `AVAILABLE`。發獎狀態：`QUEUED`、`PROCESSING`、`FAILED_RETRYABLE`、`FAILED_MANUAL_REVIEW`、`GRANTED`。資格核銷與發獎狀態分開保存，發獎失敗不會恢復成另一份可領資格。

| 情況 | 處理 |
| --- | --- |
| 沒有出貨或掃描轉傳的連結 | 不產生宅配資格 |
| 出貨中、到店待取或物流尚未確認收件 | 保留原資格，顯示等待物流確認，拒絕宅配領取 |
| 已收件但綠界尚未更新 | 等待通知或排程反查；會員自報收件不解鎖 |
| 有多份未領資格 | 使用者分別確認；請求始終指定同一份 ID，重試不消耗下一份 |
| 正式出貨前取消或過期 | 不建立資格 |
| 已建立但尚未領，包裹取消或退回 | 以來源事件撤銷原資格並釋放保留額，保留資料與原因 |
| 包裹一時配送異常 | 不增加或刪除資格，待有效來源狀態處理 |
| 配送完成被物流商有效更正撤銷 | 未領資格恢復等待收件並釋放原保留額；已核銷不重抽，進入有紀錄的帳務處理 |
| 領取交易已成功後才退回包裹 | 不自動重抽、追扣或發第二份；帳務更正需獨立、有原因的人工流程 |
| 關閉新資格建立 | 已承諾資格仍可依原規則領取 |
| 暫停領取與發獎 | 阻擋新核銷及未完成的入帳工作；恢復後沿用原紀錄，成功紀錄仍可查詢 |
| 原本漏建、漏發或入帳狀態落後 | 對帳原來源、原 claim、原 ledger，不能用新 ID 補發 |
| 切換錢包或重新登入 | 資格仍屬原會員；已建立 claim 沿用原收款錢包 |

首版不設定資格自動到期，也不因跨日、跨週或每日任務重置而清除。已入帳 Points 依既有站內 Points 政策處理。歷史資格、claim 與 ledger 都不能刪除以重置次數。

## 建議 API 契約

以下路由為待實作介面，皆從登入身分取得會員，使用 `Cache-Control: no-store`。名片與宅配分開寫入，以免通用「領下一份」介面在回應丟失時核銷別份。

| 方法與路由 | 行為 |
| --- | --- |
| `GET /v1/user/physical-gifts` | 回傳名片活動 offer、本人宅配資格及已有 claim；不抽樣、不建立名片資格 |
| `POST /v1/user/physical-gifts/welcome/:campaignId/claim` | 檢查名片活動，原子建立或取得本人同活動唯一 claim |
| `POST /v1/user/physical-gifts/entitlements/:entitlementId/claim` | 核銷本人一份宅配資格；再次請求返回原 claim |
| `GET /v1/user/physical-gifts/claims/:claimId` | 查詢本人固定結果與入帳狀態 |
| `GET /v1/user/physical-gifts/history` | 分頁列出本人見面禮、宅配禮包與入帳紀錄 |

POST 不接受金額、機率、userId 或收款錢包。伺服器產生唯一鍵；前端另外提供請求識別碼也不能突破來源限制。對不存在或不屬本人的資格及 claim 統一回應 404，不洩漏他人資料。未登入回應 401，尚未可領或活動暫停回應帶穩定 reason code 的 409，包括 `DELIVERY_NOT_CONFIRMED`、`WAITING_FUNDS`、`CLAIM_PAUSED`、`ENTITLEMENT_REVOKED`。GET 回傳等待原因與已確認的收件時間摘要，不回傳完整物流原始通知或個資。

同一份領取成功或重試的完整回應範例，ID 與數字僅供驗收 fixture：

```json
{
  "claimId": "example-claim-001",
  "entitlementId": "example-entitlement-001",
  "sourceType": "SHIPMENT",
  "status": "QUEUED",
  "reward": {
    "kind": "DATABASE_POINTS",
    "tier": "GOLD",
    "points": 5,
    "amountRaw": "5000000000000000000",
    "policyVersionId": "example-policy-v1"
  },
  "settlement": {
    "credited": false,
    "pointsLedgerEntryId": null
  }
}
```

入帳完成後沿用同一個 claim ID 與 reward，狀態變成 `GRANTED`，`credited` 為 true 並提供 ledger ID。前台不能僅因 HTTP 成功就標示已入帳。成功重試可更新結算狀態，但不得改變資格、結果或收款對象。

## 前台體驗

頁面以「你的隨機禮包」為標題，登入後列出可領內容，優先顯示宅配隨箱禮，再顯示尚未領取的見面禮。宅配項目只顯示本人包裹的出貨日期、收件確認時間與識別摘要，不暴露完整姓名、地址或電話。等待物流確認的禮包保留封存外觀與狀態文字，只有可領資格才顯示「開啟禮包」。

使用者按「開啟禮包」才 POST 指定資格。動畫使用後端回傳的結果；動畫取消、返回、刷新或重播都只改變畫面。進入處理中時保留 claim ID，重新進頁時從後端恢復，不能再次走「領下一份」。

空狀態需區分「目前沒有可領禮包」、「等待物流確認」、「這份禮包已領取」、「禮包準備中」與「獎勵入帳處理中」。物流資料已確認時，可先顯示「包裹已收件，你的隨箱禮已解鎖」，讓使用者點開後再播放拆封動畫。同頁可查看歷史。若改用不同帳號登入，顯示該帳號的資格並清除前一帳號的暫存畫面。

新增前台 `/gift` 入口及語系頁面，沿用既有登入與禮包動畫元件。新的資料介面不依賴每日任務的日期、週期或完成條件。

## Admin 操作與對帳

建議新增實體禮包管理入口，提供名片活動、宅配方案、包裹資格、領取紀錄與入帳狀態。獎池可引用既有禮包呈現素材，但實體活動獨立控制，不改變現行每日任務 evergreen 的啟用與重置行為。

營運需能發布獎池版本、設定預算、暫停新資格或領取、查看待補資與失敗紀錄，以及對帳或重試原工作。每次操作保存操作者、原因、來源與前後狀態，讀取與管理採不同權限。

裝箱或出貨畫面需記錄實際箱數與是否放入統一卡片，並顯示每箱資格建立、等待收件、待補資或可領的狀態。每箱可查看有效物流綁定、來源通知、正規化決定、收件證據及更正紀錄；商家直送的人工確認須單獨授權及留存證據。首版正常作業每箱放一張，資格來自包裹事實；忘記放卡不會自動產生第二份補償資格。

報表分別統計正式出貨包裹數、已建立資格、等待物流確認、已確認收件、待補資、未領、已核銷、已入帳、失敗及撤銷；預算顯示已支付、已承諾與仍保留的最大金額。Points 收支與來源商家依既有帳務分類紀錄，不能把贈點列為銷售收入。

對帳工具先確認有效包裹來源及最新收件證據，再使用原來源鍵補建或重試。沒有有效出貨紀錄時拒絕宅配補發；沒有有效收件證據時不能啟用。不能使用直接改餘額或新建隨機 claim 的方式修復狀態。

## 驗收案例

| 案例 | 必須成立的結果 |
| --- | --- |
| 同帳號兩個實際包裹 | 各一份資格，各可領一次 |
| 同出貨單拆兩箱 | 兩個包裹 ID、兩份資格，不以商品件數計算 |
| 名片重掃、換裝置、跨日 | 同活動同帳號仍只一筆 claim |
| 名片與宅配都有資格 | 可分別領；宅配不被名片活動限制擋住 |
| 未登入或沒有出貨 | 不因掃碼建立宅配資格 |
| 已知固定網址、尚在配送 | 可進頁查看，不能領新包裹的禮包 |
| 超商已到店、消費者尚未取件 | 維持 `PENDING_DELIVERY`，不能領 |
| 本包裹消費者成功取件或宅配送達 | 有效收件證據及預算就緒後只啟用原一份資格 |
| 收件已確認、使用收藏網址或舊卡 | 可以領原資格一次，不要求掃描本次新卡 |
| 登入別人的帳號 | 不可查詢、領取或接收入帳原帳號資格 |
| 同資格兩台裝置同時 POST | 只有一筆 claim、一次預算核銷及一筆 Points 入帳 |
| 物流通知重送、重印或訂單更正 | 原包裹仍只一份資格 |
| 有效通知跳到已送達 | 補建同一來源資格並檢查啟用，不漏發或新增第二份 |
| 假造出貨／收件、未通過驗證或版本檢查 | 不建立或啟用資格 |
| 全方位通知 `RtnCode = 1`、貨態仍未送達 | 不把 API 成功當作已收件 |
| 重送、過期、未知、時間無效的貨態通知 | 不因這筆通知新增資格或收件確認；有效反查可走原流程修復 |
| 收件狀態已提交，啟用工作執行前重啟 | 耐久工作或對帳啟用原資格，沒有第二份 |
| 一張出貨單兩箱，只有一箱送達 | 僅該箱通過物流門檻 |
| 換單後舊物流單或逆物流回報已到店 | 不解鎖目前正向包裹 |
| 配送完成更正與領取競爭 | 領取交易檢查目前有效來源；更正先提交時拒絕核銷，已成立的 claim 不重抽 |
| 尚未收件先補足預算 | 仍等待收件，不能轉為可領 |
| 綠界通知延遲或會員按「我已收到」 | 顯示等待確認；不允許會員繞過門檻 |
| 領取提交前交易回滾 | 沒有成立的 claim、核銷、結果、工作或預算扣除 |
| 提交成功但 HTTP 回應丟失 | 原資格 POST 取得原 claim，不消耗下一份 |
| 入帳成功但狀態更新前重啟 | 取得既有 ledger 並修復狀態，不重複加點 |
| 工作重跑、暫停後恢復或人工重試 | 原結果、收款錢包、識別碼保持一致 |
| 未領資格撤銷與領取競爭 | 依同一鎖定規則只有一條狀態轉移成功，不重複釋放預算 |
| 同時建立多份資格達預算上限 | 保留額不超預算；不足項目保留唯一待補資資格 |
| 更新獎池版本或宅配活動 | 舊資格保留原版本，同包裹不能再次建資格 |
| 更換錢包或凍結帳戶 | 不改寫既有 claim，遵循既有 Points 帳務限制 |
| 前台刷新、動畫重播或返回 | 僅恢復顯示，不 POST 新領取 |

整合測試需在真實 PostgreSQL 驗證唯一限制、並發交易、預算鎖定與重啟補償，不以記憶體 repository 的成功取代。API fixture 比對完整回應、出貨事件與 ledger 的 user、來源、金額及識別碼，並負向確認沒有第二筆 claim 或入帳。

## 實作順序與完成條件

1. Backend 建立包裹來源、資格與 claim schema，完成唯一限制及並發回歸測試。
2. 串接正式出貨與收件完成來源，加入物流綁定、耐久工作、通知延遲補查及漏建／漏啟用對帳；以實際箱數、到店未取、完成取件、宅配送達及更正驗證資格。
3. 實作領取交易、隨機快照、預算保留及既有 Points 入帳，完成回應丟失與程序重啟測試。
4. Admin 加入配置、裝箱、對帳與修復流程；前台加入固定入口、逐份開啟及歷史。
5. 在指定測試 API 與 worker runtime 驗證正常與失敗路徑，紀錄實際執行版本及物流代碼表。綠界官方文件指出測試環境沒有模擬物流狀態通知功能，測試需包含自建通知 fixture 與查詢 adapter 驗證；真實通知另以經授權的正式出貨驗證，不能宣稱 sandbox 已驗證實際收件。檢查使用者流程後才發布正式入口及印刷檔。

各專案實作前依其 AGENTS.md 同步指定基底分支；本規格整理未進行業務程式修改。首版達標須證明收件確認前無法領新宅配禮包、同帳號多次宅配完成收件後可各領、同份資格無法重領、入帳重試不加第二次，以及固定入口不需要重新印刷卡片。驗收後才可宣稱功能完成或線上可使用。
